# Overview

`openstack-nova-operator-kog` is a Krateo Operator Generator (KOG) blueprint. It ships
**no controller code of its own**: it hands the OpenStack Nova API, described as
OpenAPI, to Krateo's generic KOG machinery, which turns each described resource into a
native Kubernetes CRD and reconciles CRs of that kind into real Nova API calls.

Two moving parts make this work, and neither is in this repo — both are Krateo
platform components this chart depends on:

- [`oasgen-provider`](https://github.com/krateo-platformops/oasgen-provider) — watches
  `RestDefinition` objects, and for each one generates the CRD (kind + schema) and
  deploys a `rest-dynamic-controller` instance to reconcile it.
- [`rest-dynamic-controller`](https://github.com/krateo-platformops/rest-dynamic-controller)
  — the generated controller: it translates create/update/delete of a CR into the
  HTTP calls the OAS describes, carrying the Keystone token from the CR's
  `<Kind>Configuration`.

## What the chart deploys

The chart bundles a curated **subset** of the Nova OpenAPI (one file per resource
under `chart/assets/`) and, for each resource you enable, emits two manifests:

| asset | ConfigMap template | RestDefinition template | generated CRD kind |
|---|---|---|---|
| `server.yaml` | `configmap-server.yaml` | `rd-server.yaml` | `Instance` |
| `flavor.yaml` | `configmap-flavor.yaml` | `rd-flavor.yaml` | `ComputeFlavor` |
| `keypair.yaml` | `configmap-keypair.yaml` | `rd-keypair.yaml` | `ComputeKeypair` |
| `server-group.yaml` | `configmap-server-group.yaml` | `rd-server-group.yaml` | `ComputeServerGroup` |
| `aggregate.yaml` | `configmap-aggregate.yaml` | `rd-aggregate.yaml` | `ComputeAggregate` |
| `quota.yaml` | `configmap-quota.yaml` | `rd-quota.yaml` | `ComputeQuota` (off by default) |

Each OAS is stored in a ConfigMap; the paired `RestDefinition` points at it and
declares the generated GVK. The RestDefinitions are individually toggled by
`restdefinitions.<name>.enabled` ([configuration](./configuration.md)).

## Why the kinds are prefixed (not `Server`, `Flavor`, ...)

Each Nova request body is envelope-wrapped — `{ "server": {...} }`,
`{ "flavor": {...} }`, `{ "keypair": {...} }`, and so on — so the generated CR spec
carries a property literally named `server` / `flavor` / etc. If the CRD **Kind** were
also `Server`, `crdgen` would collide the kind with that property and emit an invalid
(empty-type) schema node the API server rejects. The chart therefore names the kinds
`Instance`, `ComputeFlavor`, `ComputeKeypair`, `ComputeServerGroup`,
`ComputeAggregate`, `ComputeQuota` (each configurable via
`restdefinitions.<name>.resourceKind`).

## The request flow

```
kubectl apply Instance CR
      │
      ▼
rest-dynamic-controller  ──emits──▶  X-Auth-Token: <keystone-token>
      │
      ▼
Nova Compute API (OVH / in-cluster)  ──▶  a real VM
```

The controller authenticates every call by setting `X-Auth-Token` itself, reading the
token from the Secret referenced by the CR's `<Kind>Configuration`
(`spec.authentication.apiKey.tokenRef`). That configuration object is generated by
oasgen-provider as a side effect of the `apiKey` security scheme in the OAS.

## Authentication — a native apiKey scheme, no proxy

Nova authenticates with a Keystone token in a custom `X-Auth-Token` header. OpenAPI
models exactly that as `type: apiKey, in: header`, and oasgen-provider has supported it
since **0.19.0**: the generator emits
`spec.authentication.apiKey.{tokenRef,header}` onto the `<Kind>Configuration` CRD and
rest-dynamic-controller sets the header on each request. Nothing sits between the
controller and Nova.

Earlier revisions of this chart shipped `nova-auth-bridge`, a ~30-line nginx config
that rewrote `Authorization: Bearer <token>` into `X-Auth-Token: <token>`, because the
generator then accepted only `http/basic` and `http/bearer`. That proxy has been
removed; `apiKey` expresses the requirement directly. Full rationale in
[architecture](./architecture.md).

**Token rotation belongs to a secret-manager.** Keystone tokens expire (~1h on OVH).
Point External Secrets Operator or Vault Agent at the `nova-token` Secret and let it
own minting and rotation — the chart ships no CronJob, sidecar or refresh logic, and
the Secret holds the raw token value only so a rotation path never has to know about
HTTP framing.

## Two ways to install it

1. **The chart directly** — `helm install ./chart --set nova.url=...`.
   Good for the standalone walkthroughs ([usage](./usage.md), [e2e](./e2e.md)).
2. **As a Krateo Composition** — apply the `CompositionDefinition`
   (`compositiondefinition.yaml`) so Krateo pulls and installs the published chart,
   then apply an `OpenstackNovaOperatorKog` CR to drive its values
   ([api](./api.md), [examples](./examples.md)).
